Branch handling is inconsistent: some paths derive the default branch, most hardcode 'main'.

tasks_ai/git_service.py get_default_branch (lines ~106-110) probes for main then master but RETURNS 'main' unconditionally - on a master-only repo it reports 'main', a branch that does not exist. Hardcoded 'main' lives in: pipeline.py (the merged-branch fast-track, is_merged(branch, 'main'); line ~141 integration_target), git_service.py (is_merged default target; check_main_divergence rev-parse 'main'; merge_branches('staging','main'); pipeline_map DONE->'main' at ~371), and sync_task_content's default_branch loop (utils.py) handles main/master itself. hooks/cleanup paths may also reference main directly.

Observed during task 336 testing: a fixture built with plain 'git init' got 'master' as its initial branch (git's default), so every gate/sync path in the fixture compared against a nonexistent 'main' and failed in confusing ways (is_merged fatal: Not a valid object name main; merge-base ambiguous argument). tests/test_store_concurrency.py had to init with 'git init -b main' explicitly, and tests/hammer_test_base.py similarly rewrites main from origin/main. Real users on master-named repos hit the same wall in production paths (sync_task_content, is_merged, repo merge targets, archive merge checks).

Fix direction: one authority - make get_default_branch return the first existing of main/master (or the repo's init.defaultBranch config), then replace every hardcoded 'main' in gate/sync/merge paths with that derived value, keeping 'main' only as the final fallback. Add a fixture/test that runs the pipeline on a master-named repo end to end (create -> move -> checkpoint -> gate -> merge) and a test that a repo with NEITHER main nor master fails with a clear message instead of a git fatal.
