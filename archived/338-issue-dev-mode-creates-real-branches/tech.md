Root cause: --dev only swaps the STORE. tasks_ai/context.py ProjectContext.__init__ sets tasks_path to HAMMER_DEV_TASKS_DIR (/tmp/.tasks) when dev=True, but main_repo_root still resolves via git rev-parse --git-common-dir from the process cwd, i.e. the real repo. Every subsystem below the store therefore acts on the real repo: WorktreeManager.create_task_worktree runs git worktree add in main_repo_root (worktree_manager.py), the counter recovery path _recover_task_counter_from_tasks scans real state, the guard compares the dev store's ids against the real repo's local branches, and is_merged/fetch run against the real repo.

Observed consequences (task 336 session, all cleaned up manually): (a) dev creates left real branches 335-task-undo-clean-repro and 336-task-write-user-tests-for-335-undo; (b) the second then collided with the real task 336's id, and the guard rejected the real promotion with 'duplicate task ID 336. multiple local branches claim id 336', halting the pipeline until the stray branch was deleted by hand; (c) a dev create also allocated ids that had to be manually reconciled.

Fix direction - pick one, smallest correct: (1) dev mode refuses every operation that touches the main repo (create, mount, move-with-worktree, guard checks) with a clear error, leaving only store-level commands (list/show/move between store folders) runnable; or (2) dev mode binds every git operation to a throwaway repo - e.g. a temp clone created on first dev invocation and reused per HAMMER_DEV_TASKS_DIR; or (3) dev mode uses a dedicated refs namespace so dev writes cannot collide with task branches. Option 1 is the lazy-correct floor and matches the documented purpose of --dev ('testing tool behavior'); options 2/3 add isolation for tests that need real git.

The guard failure mode in (b) is the same class task 336 fixed for concurrency: shared refs with no scoping. Do not paper over it with more --force usage.
