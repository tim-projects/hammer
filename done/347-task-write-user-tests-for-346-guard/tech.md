Correction to what I reported after task 344: hammer-created worktrees already satisfy this invariant by construction - tasks_ai/worktree_manager.py:103 does worktree_path = os.path.join(self.worktrees_base, branch), so the directory basename IS the branch name. The 344 incident was not a mismatch: tasks_ai/commands/create.py:93 truncates the slug to 30 chars (branch '344-task-pipeline-should-auto-push-bran'), and typing the untruncated slug created a stray directory outside the worktree. So this rule defends against what hammer does not create: a hand-run 'git worktree add <other-path> <branch>', a moved/renamed worktree directory, or a stale manifest entry whose path basename drifts from its branch. The guard already sees both halves of the data - tasks_ai/guard_engine.py parses 'git worktree list --porcelain' (branch + worktree path per entry) in _worktree_list() and audits worktrees in _compute_anomalies (~line 453), where it flags GUARD_WORKTREE_ORPHAN for duplicate worktrees per task and for worktrees checking out a missing branch, but never compares the worktree directory basename against the branch. GuardGateHook (tasks_ai/pipeline_hooks.py) turns any finding into a rejected transition, so a new code here blocks REVIEW/STAGING/DONE/ARCHIVED the same way.
