Root cause: repo.py cmd_merge previously classified only the source branch as a task. For a merge such as main -> task branch, its generic fallback ran git checkout in the main worktree, which fails when the destination branch is already checked out in a registered task worktree. Current task-451 implementation adds registered_task_worktree() to resolve the destination through WorktreeManager and cmd_merge_task_worktree() to merge in that worktree without changing the main worktree. The helper verifies the registered worktree is on the target branch, refuses dirty worktrees, performs a fast-forward-only pull, aborts failed merges, and optionally pushes the target. Existing task-source to pipeline-target merges still route through the gated tasks move path before the fallback. Regression coverage is in tests/test_repo_worktree_root.py: test_repo_merge_uses_registered_task_worktree verifies main remains checked out and main becomes an ancestor of the task branch; test_repo_merge_refuses_dirty_task_worktree verifies uncommitted work and the task ref are preserved. The task-451 branch commit is 2f61efb1.
