Background: .tasks is a single shared git repo (branch 'tasks', remote origin/tasks) at the main repo root. It is gitignored in the main repo (.gitignore: /.tasks/; git ls-files .tasks = 0), and ProjectContext (tasks_ai/context.py:22) always resolves tasks_path to <main_repo_root>/.tasks, so every worktree and every agent session writes to the same store. That central-store model is by design; three checkpoint defects make it unsafe under concurrency.

PROBLEM 1 - Cross-task store bleed (commands/checkpoint.py:16-17). runs git add --all then git commit in cli.tasks_path. add --all stages EVERY pending change in the shared store: other agents' uncommitted moves (perform_move does shutil.move with no commit, tasks_ai/utils.py), other agents' task folders mid-creation, doctor/unlink/delete repairs, and undo temp dirs (mkdtemp(dir=tasks_path), cli.py:1136). All of it is committed under the message 'Cp: <your task>'. Consequences: (a) store history attributes another task's state change to the wrong task; (b) undo scans the store's global history (git log --all) and substring-matches folder names (cli.py:1101,1119,1128), so it picks up these bleed commits and can restore ANOTHER task's files while 'undoing' task N - undo is unsafe until this is fixed; (c) because moves commit nothing themselves, the only commits come from whichever checkpoint runs next, so the store has no per-transition commit correlation.

PROBLEM 2 - Silent git failures (cli.py:269 _run_git(check=False) default; checkpoint.py ignores both return codes). With parallel agents, git index.lock contention in the shared store is routine, not exceptional. A checkpoint whose add or commit fails still logs 'Done.' and returns success JSON: notes are written to disk but never committed, and the next add --all may or may not pick them up. The store silently loses updates with no signal to the agent.

PROBLEM 3 - Dead or cwd-dependent sync (sync_task_content, tasks_ai/utils.py:65-110). (a) The parts-sync branch runs git diff -- <task dir relpath from cli.root> in the MAIN repo, where .tasks is ignored - verified empirically: git diff --name-only -- .tasks/progressing returns empty, so edits to story/tech/plan/criteria markdown never propagate into the record. Only current-task.md (utils.py:84-89) and the branch commit list (utils.py:79-83) actually sync. (b) git log branch^main and rev-parse calls run with cwd=None, i.e. the agent's process cwd: from a task worktree this happens to work because branches are shared refs, but from any non-repo cwd it fails silently and reports no commits. Result: 'all task updates written back to the central store' is half-implemented and location-dependent.

Out of scope (tracked separately): task-id allocation race (tasks_ai/counter.py, no lock), worktrees.json manifest read-modify-write race (tasks_ai/worktree_manager.py), guard gate fast-track hole via is_merged on zero-commit branches (docs/spec-worktrees.md section 10.1, task 241), undo substring id matching (cli.py:1090-1160).
