Every store WRITE path added by tasks 328/336 takes the exclusive store lock (commit_task_paths, counter allocation, manifest mutations, undo), but no store READ path takes anything: task_service.find_task, the list command, commands/current, and guard_engine's refresh/scan all walk the working tree of the shared .tasks repo directly.

Consequences under simultaneous work: (a) sync_task_content's pending-change check ('git status --porcelain -- <rel task dir>' in the STORE repo) reports the writer's in-flight files - so agent B's checkpoint can claim and commit changes agent A is still writing; (b) a list during another agent's move can show the stale state folder (the two-folder window from the move task); (c) the guard's SQLite cache is rebuilt from this mid-transaction view, caching a state that never existed at a commit boundary; (d) none of it is visible in git history, so the corruption leaves no trace.

Fix direction: give the lock a shared mode and have readers take LOCK_SH while writers keep LOCK_EX (fcntl allows both on the same lock file; readers then block only during a write transaction). Apply it to the store-reading helpers: find_task, list/current, and the guard's refresh. This keeps the lock file as the single serialization point and needs no new mechanism. Alternative - read from git HEAD instead of the working tree - is a bigger change and breaks the pending-changes signal that checkpoint depends on. Note the interplay: readers taking LOCK_SH must not run inside a writer's transaction in the same thread (the lock is reentrant for exclusive, so a nested shared request would pass through and observe the in-flight state - acceptable, since the writer is the one observing its own writes).
