Introduced by the task 338 batch (dev isolation), colliding with the test harness.

Mechanism A - direct failures: tests/hammer_test_base.py run_tasks hardcodes ['tasks','-j','--dev'] + args for EVERY command. Since task 338, the --dev FLAG does two more things beyond swapping the store: (1) ProjectContext (tasks_ai/context.py _ensure_dev_repo) re-points repo_root/main_repo_root at <store>-repo, a throwaway clone of the invoked repo; (2) GitService.push_tasks_branch refuses to push ('push refused in --dev mode'). So every harness test that (a) exercises save/push semantics or (b) inspects the fixture repo while the CLI wrote to the clone (worktree paths, mount, merge outcomes) now fails - test_repo_save_with_mock_remote outright (the refusal), the worktree-ownership/naming/worktree_system families by path mismatch.

Mechanism B - cascade: some in-suite failures only appear in the full run. Evidence (Popen TypeError NoneType, files passing alone) is consistent with a mid-test failure skipping tearDown and leaking process state - the leaked env var HAMMER_DEV_TASKS_DIR or a deleted cwd - into every later file. This class still needs RCA during implementation; do not assume it is only mechanism A.

Fix direction: 1) Primary - HammerTestBase.run_tasks should stop passing --dev and isolate the store via HAMMER_DEV_TASKS_DIR alone. tasks_ai/cli.py:158 already supports this: the store path is overridden when 'dev or os.environ.get(HAMMER_DEV_TASKS_DIR)', while ProjectContext is constructed with dev=args.dev (cli.py:124) - with the flag dropped, repo_root stays the fixture repo, which is exactly the semantics every workflow test was written against. 2) Make the base fixture leak-proof (try/finally around env and cwd) so a failing test cannot poison later files. 3) Tests that legitimately test dev behavior (tests/test_dev_isolation.py, tests/test_dev_mode.py) must pass --dev explicitly themselves. 4) Re-run the full suite and drive it to zero failures except task 326's four pre-existing test_robustness failures.
