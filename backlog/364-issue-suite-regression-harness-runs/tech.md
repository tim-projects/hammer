Introduced by the task 338 batch (dev isolation) colliding with the test harness. The harness MUST keep --dev - see the isolation note below; the earlier draft of this task wrongly proposed dropping the flag.

Evidence on main@f928f3d9 (2026-11-08): full suite 55 failed / 162 passed / 1 skipped, against 4 pre-existing failures on task 336's branch. Two failure classes:
A) Standalone: tests/test_repo.py alone fails test_repo_save_with_mock_remote with "'./hammer tasks save' is refused in --dev mode" (task 338's push refusal).
B) In-suite-only cascade: test_worktree_system.py and test_store_concurrency.py pass standalone, fail in the full run with Popen 'expected str, bytes or os.PathLike object, not NoneType' - consistent with a mid-test failure skipping tearDown and leaking HAMMER_DEV_TASKS_DIR or a deleted cwd into later files.

Mechanism: HammerTestBase.run_tasks hardcodes ['tasks','-j','--dev']+args (tests/hammer_test_base.py). Since 338 the --dev flag (a) refuses pushes in push_tasks_branch and (b) re-points repo_root at <store>-repo, a throwaway clone of the invoked repo (tasks_ai/context.py _ensure_dev_repo). Every harness test that inspects the fixture repo while the CLI wrote to that clone (worktree paths, mount, merge outcomes) or that exercises save semantics now fails.

ISOLATION NOTE - why the flag stays: with the flag dropped, the store is still redirected by HAMMER_DEV_TASKS_DIR (tasks_ai/cli.py:158), but push_tasks_branch falls back to the parent repo's remote when the store has none, and the fixture clone's origin IS the real repo (setUp clones os.getcwd()). Verified in a /tmp sandbox: 'HAMMER_DEV_TASKS_DIR=... hammer tasks save -y' logged 'Adding parent remote /tmp/iso_real to .tasks for sync' - in the real harness that is the real repo, so any harness test calling save would push test state into production. The --dev flag is what makes that impossible; removing it trades a red suite for a data hazard.

Fix direction: (1) refine dev's push refusal to the actual hazard: refuse only when the push target is the parent repo's remote (after the fallback adds it); a store whose origin is a deliberately configured local/mock remote (MockGitRemote) may push, so the save test passes. (2) make repo-swap-aware tests resolve the CLI's repo as <store>-repo (deterministic from HAMMER_DEV_TASKS_DIR) or read paths from the tool's JSON output instead of assuming repo_path/.task-worktrees. (3) leak-proof the base fixture: try/finally around the env var and cwd so one failing test cannot poison later files. (4) drive the suite to zero failures other than task 326's four pre-existing test_robustness failures. Tests that genuinely test dev behavior keep --dev explicitly.
