Background: .tasks is one shared git repo (branch 'tasks', remote origin/tasks) at the main repo root, written by every worktree and every agent session (tasks_ai/context.py:22). There is currently no locking anywhere in tasks_ai/. These four defects were descoped from task 328 (checkpoint bleed/silent-failure/sync). Task 328's pathspec-scoped checkpoint is a prerequisite for defect 4 to be meaningful; this task assumes it has landed.

DEFECT 1 - Task-id allocation race (tasks_ai/counter.py, TaskCounterProtector.get_next_id). Reads .task_counter, increments, _atomic_write, writes hash, then git add+commit. No lock around the read-modify-write. Two agents running tasks create concurrently (or create from two worktrees) allocate the SAME id. Consequences: two tasks claim one id in the store; the guard rejects both forever after (GUARD_DUPLICATE_ID, GUARD_STATE_DUPLICATE); the existing hash-mismatch recovery path only fires on tampering, not on genuine racing. Fix: serialize the counter transaction (flock on a .tasks lock file, or derive the id inside a single git commit), keep hash verification intact, and add a test where two allocations race and assert distinct ids.

DEFECT 2 - worktrees.json manifest read-modify-write race (tasks_ai/worktree_manager.py). Every mount/create/remove/prune does _load_manifest -> mutate in memory -> _save_manifest (tmp write + os.replace of the whole file). No lock. Two agents mounting two tasks concurrently: last replace wins and the first task's entry silently disappears. Consequences: manifest drift; GUARD_WORKTREE_ORPHAN false hits at the next gate; mount for an existing task re-runs git worktree add (fails because the path exists, falls back to creating a second branch claiming the same id -> duplicate-branch guard reject); prune/remove then delete entries another session just wrote. Also interaction with spec-known limitation: stale entries persist until cleanup because .task-worktrees/ is gitignored and detection is path-existence only. Fix: one mutation path with a lock around load->save; add a concurrent-mount test asserting both entries survive.

DEFECT 3 - Promotion gate hole via is_merged (tasks_ai/pipeline.py:80 fast-tracks REVIEW/STAGING/DONE when git.is_merged(branch, main) is true; tasks_ai/git_service.py:108-122). is_merged does fetch --all in the main repo root on EVERY gate check, then git merge-base --is-ancestor branch origin/main. A freshly created task branch with zero commits beyond main is an ancestor, so a task with no work done fast-tracks to DONE. Consequences: an agent that produces no code can drive a task to DONE; the gate is a no-op for exactly the tasks it should stop. Secondary: fetch --all per gate mutates shared remote-tracking refs for all sessions mid-flight and fails closed offline. Documented as spec limitation 10.1 / task 241. Fix: fast-track must require the branch to be ahead of main (>=1 commit, or non-empty diff), or be removed; move remote-ref refresh out of the gate into an explicit sync. Test: branch with zero commits must NOT fast-track; branch merged with commits still does.

DEFECT 4 - Undo is unsafe and degrades (tasks_ai/cli.py:1090-1160). (a) Commits are found by SUBSTRING match: fname in ls-tree output, so folder 1-task-foo matches any commit containing 11-task-foo, 21-task-foo, ... - undo restores the wrong task's files. (b) It scans the store's GLOBAL history (git log --all) and restores from the second-most-recent commit containing the folder name; commits that merely touched the folder via another task's bleed (or another agent's checkpoint) get picked, so undoing task N can rewind task M. (c) tempfile.mkdtemp(dir=tasks_path) creates temp dirs inside the store; any concurrent add sweeps them in. (d) The scan is O(store commits) subprocess calls per undo and gets slower with every agent's checkpoint. (e) The 'Cannot undo twice' check reads a GLOBAL commit subject. Fix: match paths exactly (path == folder prefix + '/'), scope history to git log -- <folder>, put temp files outside the store, reuse the locked store-mutation helper from 328, and test with similarly-named ids (1 vs 11) plus a commit that only touches another task.
