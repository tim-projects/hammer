Root cause: TasksCLI.__init__ (tasks_ai/cli.py, the dev branch) does os.makedirs(self.tasks_path, exist_ok=True) before any command runs, so by the time init() executes the store directory always exists. init()'s dev branch then tests bare existence (tasks_ai/cli.py:647: 'if os.path.exists(self.tasks_path): error(already initialized)') and refuses. The non-dev branch (cli.py:692) checks differently and works.

Consequences: (1) the documented dev flow ('./hammer tasks --dev init' then '--dev list') is dead at step one on any fresh path; (2) the refused path leaves behind a non-git store directory, and every subsequent dev command silently degrades: store_is_git() is false, so commit_task_paths returns without committing and writes to disk only - dev-mode data is never committed while the CLI reports success (observed directly: two separate fresh dev stores, task folders written, zero commits, worktree/manifest state inconsistent between runs); (3) anything that ran before this regression in dev mode (task 338's own fixtures set HAMMER_DEV_TASKS_DIR per test) can now leave this half-store behind and corrupt later dev runs.

Fix direction: the dev branch must test whether the store is actually initialized, not whether the directory exists - check for the store's git repo (os.path.exists(os.path.join(tasks_path, '.git'))) or task data, matching the non-dev branch's condition; a fresh empty directory must proceed to initialize. Also make the refused-without-force path not leave a half-created non-git store behind (either initialize it properly or clean the empty dir). Prefer fixing the check over making init idempotent-by-force, because 'init --force' backs up and wipes: on a non-git store the backup semantics are meaningless.
