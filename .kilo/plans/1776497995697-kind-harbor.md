# Worktree-Based Task Management System

## Overview
This proposal describes a major rework of the hammer system to use git worktrees for task isolation instead of relying solely on branches. Each task would have its own dedicated worktree, allowing truly independent development while maintaining the ability to merge completed work back into the main project.

## Current Limitations
- All tasks share the same working directory, causing context switching overhead
- Branch-based isolation doesn't prevent file system level interference
- Difficult to work on multiple tasks simultaneously without stashing/committing
- Long-running tasks block the main working directory

## Proposed Solution
### Worktree-per-Task Model
1. Each task gets its own git worktree checked out from main
2. Inside each worktree, tasks can still use branches for internal development
3. Worktrees are stored in a structured directory (e.g., `.tasks/worktrees/`)
4. Main repository remains clean and always represents the integrated state

### Workflow Changes
1. **Task Creation**: 
   - Create worktree: `git worktree add .tasks/worktrees/<task-id>-<slug> main`
   - Initialize task metadata in worktree
   - Set worktree as active context for task operations

2. **Development**:
   - All task operations occur within the task's worktree
   - Internal branching still supported for complex tasks
   - Validation, testing, and commits happen in isolation

3. **Task Completion**:
   - Merge worktree changes back to main via standard merge process
   - Handle conflicts through established conflict resolution workflow
   - Clean up worktree after successful merge

### Technical Implementation
#### Core Changes Required:
1. **Worktree Management**:
   - Add worktree creation/deletion commands to tasks.py
   - Modify repo.py to detect and operate within worktrees
   - Update file paths to be worktree-relative where appropriate

2. **State Tracking**:
   - Track worktree paths in task metadata
   - Update progress tracking to reference worktree locations
   - Ensure activity logs and checkpoints work within worktrees

3. **Integration Process**:
   - Enhance repo.py merge logic to handle worktree-to-main merges
   - Implement automated conflict detection and reporting
   - Provide tools for manual conflict resolution when needed

4. **Cleanup Procedures**:
   - Automated worktree removal after successful merge
   - Preserve worktrees for failed tasks for debugging
   - Worktree cleanup commands for manual intervention

### Benefits
- True parallel development on multiple tasks
- No context switching between tasks
- Each task gets a clean, isolated environment
- Reduced risk of accidental cross-task contamination
- Ability to pause/resume tasks without affecting others

### Challenges and Mitigations
- **Disk Space**: More working directories = more space used
  - Mitigation: Implement worktree cleanup policies
  - Mitigation: Allow configurable worktree storage location
  
- **Complexity**: Additional layer of abstraction
  - Mitigation: Clear documentation and workflow guides
  - Mitigation: Maintain backward compatibility where possible
  
- **Merge Conflicts**: Potential for more complex merges
  - Mitigation: Encourage frequent small merges
  - Mitigation: Improve conflict resolution tooling
  - Mitigation: Better conflict preview and resolution workflows

### Implementation Phases
1. **Phase 1**: Basic worktree creation/deletion infrastructure
2. **Phase 2**: Redirect task operations to worktrees
3. **Phase 3**: Implement worktree-to-main merge workflow
4. **Phase 4**: Add conflict detection and resolution tools
5. **Phase 5**: Optimize and cleanup

### Backward Compatibility
- Maintain branch-based workflow as fallback option
- Allow configuration to choose between worktree/branch modes
- Ensure existing tasks continue to work during transition

### Configuration Options
- `tasks.use_worktrees`: Boolean to enable/disable feature
- `tasks.worktree_dir`: Directory for storing worktrees (default: `.tasks/worktrees`)
- `tasks.auto_cleanup`: Automatically remove worktrees after merge (default: true)

## Open Questions
1. How should we handle tasks that already exist in the current branch-based system?
2. What happens to the `.tasks` directory itself in worktrees - should it be shared or isolated?
3. How do we handle shared dependencies or virtual environments across worktrees?
4. Should we implement worktree pruning/cleanup policies for stale work?
